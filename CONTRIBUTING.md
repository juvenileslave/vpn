# Участие в проекте

Репозиторий содержит архитектурный план и инструменты работы с репозиторием.
Реализация и развёртывание VPN не входят в его текущее состояние.
[Архитектурный план](docs/ARCHITECTURE_PLAN.md) описывает целевую систему, а не
готовые команды эксплуатации.

## Обязательный процесс

Владелец репозитория — [@juvenileslave](https://github.com/juvenileslave);
правила владения файлами заданы в [.github/CODEOWNERS](.github/CODEOWNERS).

Декларации серверных настроек: [репозиторий](.github/repository.json),
[master](.github/rulesets/master.json) и
[release-теги](.github/rulesets/release-tags.json).
Правила активированы в GitHub: [master](https://github.com/juvenileslave/vpn/rules/26988307),
[release-теги](https://github.com/juvenileslave/vpn/rules/26988138).
Изменение JSON само по себе не меняет GitHub: после согласованного PR настройки
нужно применить через API и проверить ответ сервера.

- Основной репозиторий — `juvenileslave/vpn`, форк разработчика — `popularhono/vpn`.
  Рабочий аккаунт `popularhono` не имеет прав записи в основной репозиторий.
- Основная ветка — `master`; feature-ветки создаются от актуальной
  `upstream/master` и отправляются только в форк. PR направляется из форка в
  `juvenileslave/vpn:master`.
- Прямые изменения `master` запрещены после первоначального bootstrap-коммита;
  настройки репозитория меняются тем же PR-процессом.
- Перед слиянием обязательны успешные проверки с точными именами
  `Repository checks` и `Secret scan`. Ветка PR должна быть актуальна относительно
  текущей `master`, а все обсуждения — разрешены.
- Разрешён только squash merge; обычный merge и rebase merge отключены.
- Force push и удаление защищённой ветки запрещены. Правила действуют и для
  администраторов; административный обход не является рабочим процессом.
- Обязателен один approval от CODEOWNER `juvenileslave`. Последний push должен
  одобрить другой аккаунт; новые коммиты сбрасывают старое approve. Рабочий
  аккаунт `popularhono` создаёт PR, основной аккаунт `juvenileslave` выполняет
  review и squash merge. Рабочий агент не использует основной токен.
- Теги релизов `v*` нельзя переписывать или удалять. Исправленный релиз получает
  новый тег.

GitHub Actions разрешены только для GitHub-owned actions; ссылки закрепляются
полным SHA. По умолчанию `GITHUB_TOKEN` имеет только read-доступ и не может
одобрять PR. Запуски из внешних fork требуют одобрения владельца.
Включены GitHub secret scanning, push protection, Dependabot alerts/security
updates и приватные сообщения об уязвимостях. Dependabot проверяет GitHub
Actions и Python-зависимости еженедельно.

Если настройки GitHub не соответствуют этим требованиям, сначала восстановите
защиту, а не используйте её отсутствие для слияния.

## Локальная работа

1. Проверьте аккаунт командой `gh api user --jq .login`: для разработки это
   `popularhono`. В рабочем клоне `origin` — `popularhono/vpn`, `upstream` —
   `juvenileslave/vpn`. Выполните `git fetch upstream` и создайте feature-ветку
   от `upstream/master` с понятным именем.
2. Подготовьте окружение командой `make bootstrap`, затем установите локальные
   hooks командой `make hooks`.
3. Внесите ограниченное изменение. Не меняйте архитектурный план без отдельного
   явного согласования; обновляйте связанную документацию вместе с кодом.
4. Просмотрите diff и подготовьте к коммиту только явно выбранные публичные
   файлы. Новые файлы добавьте в индекс до запуска `make check`: эта команда
   проверяет публичные tracked/staged-файлы, а не все локальные материалы.
5. Выполните `make check`, создайте коммит в feature-ветке и отправьте её:
   `git push -u origin <branch>`. Откройте PR в `juvenileslave/vpn:master`
   с head `popularhono:<branch>`. Заполните
   [шаблон PR](.github/pull_request_template.md): цель, фактические проверки,
   риски и способ отката.
6. Дождитесь обязательных проверок GitHub и устраните замечания. Если CI
   внешнего PR ожидает разрешения, передайте ссылку владельцу; не обходите
   ожидание его токеном. Для обновления опубликованной ветки используйте
   `git fetch upstream` и `git merge upstream/master`, затем обычный push.
7. Передайте готовый PR владельцу `juvenileslave` для review и squash merge.
   Не сливайте PR рабочим аккаунтом и не меняйте защиту ради слияния.

`make check` разрешён и на `master`: сама проверка не меняет ветку. Локальный
commit hook запрещает коммиты в `master` и `main`. Hooks — дополнительная защита,
а не замена серверным правилам и CI; не обходите их ради публикации изменения.

Whitespace/EOF hooks могут исправлять файлы, кроме архитектурного плана.
Просмотрите исправления, повторите `make check` и обновите индекс перед коммитом.
`make check` не сканирует всю историю Git: поиск приватных ключей в выбранных
файлах не заменяет отдельный CI job `Secret scan`, который сканирует доступную
историю Git через gitleaks.

## Границы публикации

- Не добавляйте секреты, рабочие конфигурации серверов, дампы, историю приватных
  обсуждений или неотредактированные журналы. Не переносите их в commit message,
  PR, issue, скриншоты или вывод проверки.
- Используйте только обезличенные примеры. Для багов достаточно минимального
  воспроизведения без реальных адресов, идентификаторов и учётных данных.
- Уязвимости сообщайте приватно по [SECURITY.md](SECURITY.md), а не через issue.
- Не запускайте развёртывание, не меняйте DNS, firewall, сертификаты или рабочие
  сервисы в рамках обычного изменения репозитория. Для production-действий
  требуется отдельное явное разрешение владельца и согласованный откат.

## Проверки и откат

В PR записывайте только реально выполненные проверки и их результат. Незапущенную
проверку обозначайте прямо с причиной; локальный успех не доказывает успех CI или
работоспособность VPN. Команды из архитектурного плана нельзя выдавать за
реализованные инструменты этого репозитория.

Откат изменения репозитория — отдельный PR, отменяющий соответствующий
squash-коммит, с теми же проверками и правилами слияния. Не переписывайте историю
`master`. Если изменение имеет внешние эффекты, заранее опишите их отдельный
откат: отмена Git-коммита сама по себе не восстанавливает внешнее состояние.
