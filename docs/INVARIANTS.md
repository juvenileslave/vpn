# Операционные инварианты

Правила, которые действуют независимо от задачи (этап 0.4
[архитектурного плана](ARCHITECTURE_PLAN.md): перенос уроков в «инварианты»).
Решения архитектуры собраны в [реестре решений](DECISIONS.md).

- **Статус:** действующий; дата: 2026-11-10.
- **Источник истины:** [docs/ARCHITECTURE_PLAN.md](ARCHITECTURE_PLAN.md),
  [AGENTS.md](../AGENTS.md), [CONTRIBUTING.md](../CONTRIBUTING.md) и
  [README.md](../README.md). При расхождении правы они.
- **Состояние реализации:** VPN не реализован и не развёрнут. Для правил о
  будущей эксплуатации проверка описывает требуемый способ, а не существующую
  автоматизацию.

Каждый пункт содержит правило, причину и способ проверки или обеспечения.

## Репозиторий и публикация

1. **Нет прямых коммитов в `master`.**
   - Правило: изменения идут только через feature-ветку форка и PR в
     `juvenileslave/vpn:master`; нужны успешные `Repository checks` и
     `Secret scan`, актуальная база, разрешённые обсуждения и approval
     CODEOWNER `juvenileslave`. Force push, удаление ветки и административный
     bypass запрещены; рабочий агент не одобряет и не сливает PR.
   - Почему: каждое изменение проходит review владельца и обязательные проверки.
   - Проверка: ruleset `master` в GitHub ([декларация](../.github/rulesets/master.json)),
     локальный hook `no-commit-to-branch`, review владельца. Подробно —
     [CONTRIBUTING.md](../CONTRIBUTING.md), [AGENTS.md](../AGENTS.md),
     [README.md](../README.md).

2. **В публичном репозитории нет секретов и рабочих данных.**
   - Правило: не публикуются учётные данные, ключи, токены, реальные адреса,
     имена и идентификаторы серверов, рабочие конфигурации, дампы и экспорт
     приватных переписок — ни в файлах, ни в commit message, PR и issue.
   - Почему: репозиторий публичный; утечка не отменяется последующим удалением.
   - Проверка: `make check` (политика путей `scripts/check_repository.py`,
     `detect-private-key`), CI job `Secret scan` по истории Git, чек-лист
     [шаблона PR](../.github/pull_request_template.md) и просмотр diff;
     `.gitignore` проверку не заменяет. См. [AGENTS.md](../AGENTS.md),
     [CONTRIBUTING.md](../CONTRIBUTING.md).

3. **`docs/ARCHITECTURE_PLAN.md` сохраняется побайтно.**
   - Правило: план не переписывается и не форматируется; изменение требует
     отдельного явного поручения владельца.
   - Почему: план — исходный документ и источник истины для реестра решений.
   - Проверка: `git diff upstream/master -- docs/ARCHITECTURE_PLAN.md` пуст;
     whitespace/EOF hooks исключают файл; пункт шаблона PR; review владельца.
     См. [AGENTS.md](../AGENTS.md), [README.md](../README.md).

4. **Изменения production только с явного разрешения.**
   - Правило: без отдельного явного разрешения владельца на конкретные действия
     не выполняются развёртывание и изменения production, DNS, firewall,
     сертификатов, маршрутизации и VPN. Разрешение менять репозиторий не
     распространяется на инфраструктуру.
   - Почему: внешние изменения не откатываются отменой коммита.
   - Проверка: в PR и отчёте указывается, что production-действия не
     выполнялись либо разрешены, с планом отката. См. [AGENTS.md](../AGENTS.md),
     [CONTRIBUTING.md](../CONTRIBUTING.md), [README.md](../README.md).

## Диагностика и тестирование

5. **Тест «напрямую из РФ» — только через физический интерфейс.**
   - Правило: тест российского пути привязывается к физическому интерфейсу, а не
     идёт через TUN.
   - Почему: через TUN трафик уходит в уже работающий туннель, и тест измеряет
     не тот путь.
   - Проверка: в отчёте теста указан интерфейс (см. задачу 3.6 плана);
     результат без привязки не засчитывается.

6. **Серверный self-test не доказывает клиентский путь.**
   - Правило: работоспособность для клиента подтверждается только тестом с
     клиентской стороны.
   - Почему: проверка на сервере не проходит через сеть клиента, фильтры по
     пути и клиентскую конфигурацию.
   - Проверка: в отчёте отдельно указаны серверная и клиентская проверки;
     отсутствие клиентской обозначается прямо.

7. **Одинаковый внешний IP не различает туннели.**
   - Правило: чтобы определить, каким путём прошёл трафик, смотрите счётчики
     inbound'ов и outbound'ов, а не внешний IP.
   - Почему: разные профили выходят через один exit и показывают один адрес.
   - Проверка: вывод о пути подтверждается счётчиками (см. проверку этапа 6
     плана).

8. **XMUX и `flow` — не исправления по умолчанию; fingerprint и SNI — через A/B.**
   - Правило: XMUX и `flow` не включаются «для исправления»; смена fingerprint
     или SNI выполняется только после A/B-пробы.
   - Почему: эти параметры не устраняют известные проблемы гарантированно и
     могут ухудшить работающий профиль.
   - Проверка: изменение параметров сопровождается результатами A/B-пробы в PR
     (раздел плана «Описание для агентских систем»).

9. **Наблюдение одной сети или ASN не универсально.**
   - Правило: результат пробы относится к сети, из которой он получен; вывод о
     блокировке «везде» не делается по одной сети или ASN.
   - Почему: фильтрация различается у провайдеров; relay в датацентре не равен
     домашнему или мобильному провайдеру, а SNI проверяется в каждой сети
     отдельно.
   - Проверка: в результате пробы указана точка наблюдения; выводы сверяются с
     внешними пробами (этап 8 плана).

10. **`ssh.socket` не сломан из-за выключенного `ssh.service`.**
    - Правило: выключенный `ssh.service` не считается признаком неисправности
      SSH, если используется socket activation через `ssh.socket`.
    - Почему: при socket activation `sshd` запускается сокетом; «исправление»
      службы может нарушить доступ по SSH.
    - Проверка: перед выводом проверяется состояние `ssh.socket` и фактическое
      подключение; изменения SSH — только по разрешению (пункт 4).

## Эксплуатация

11. **Страница подписки: фиксированный `Host`, без `X-Real-IP`, мягкий лимит.**
    - Правило: прокси страницы подписки передаёт фиксированный `Host`, не
      передаёт `X-Real-IP`, а лимит запросов не ниже 240r/m.
    - Почему: прошлые проблемы с проксированием подписки; слишком строгий лимит
      ломает обновление у клиентов.
    - Проверка: review конфигурации прокси при её реализации (задачи 2.2 и 6.6
      плана); сейчас прокси в репозитории нет.

12. **Бэкап не доказан, пока не проверено восстановление.**
    - Правило: бэкап считается рабочим только после восстановления на чистой VM
      с рабочим результатом.
    - Почему: в прошлый раз восстановление не проверяли.
    - Проверка: проверка этапа 2 плана — восстановление из бэкапа даёт рабочую
      панель; результат фиксируется в отчёте.
