# Алерты метрик: состояние, доставка и CLI

Пакет `vpnctl/internal/alerts` — stateful-часть задач 10.2/10.3
[архитектурного плана](ARCHITECTURE_PLAN.md) и решения D-010: воркер по
расписанию вычисляет принятые пороговые правила
([METRICS.md](METRICS.md)), хранит состояние каждого правила в SQLite
([STATE_STORE.md](STATE_STORE.md)) и отправляет одно уведомление при переходе в
`firing` и одно при восстановлении через принятый sink
([TELEGRAM_BOT.md](TELEGRAM_BOT.md)).

Пакет не содержит второго HTTP- или Telegram-клиента: запросы выполняет
`metrics.Client`, доставку — `notify.Sink`. Планировщика вне этого пакета,
PNG-графиков, `/metrics` и `/mute` в боте, Grafana, Alertmanager, автоматической
ремедиации и paging-гарантий нет.

## Поток одного цикла

```text
config + rules  ->  ValidateRules (0 запросов при ошибке)
                ->  run lock (SQLite alert_runs)
                ->  metrics.Evaluate: один instant-запрос на правило
                ->  decide(): ok | firing | unknown + flap/grace
                ->  CommitAlertTransition: состояние + outbox в одной транзакции
                ->  ExpireAlertOutbox / PruneAlertOutbox
                ->  delivery: outbox -> notify.Sink (bounded backoff)
```

Один цикл выполняется последовательно; повторный `Cycle` в том же процессе
пропускается (`Result.Skipped`). Второй процесс с той же базой не выполняет
цикл, пока действует lease в `alert_runs`. Дополнительно каждая запись
состояния — compare-and-swap по `revision`, поэтому даже перекрывающиеся циклы
не создают два одинаковых уведомления.

## Конфигурация

Обе секции необязательны для схемы конфигурации и обязательны для
соответствующих команд. Неизвестные поля, неверные типы и значения отклоняются
так же строго, как остальной файл.

```yaml
metrics:
  endpoint: https://metrics.example.com/select/0/prometheus
  token_env: VPNCTL_METRICS_TOKEN
  timeout: 10s
  interval: 60s
alerts:
  state_db: alerts.db
  grace: 5m
  flap_samples: 2
  retention: 24h
  outbox_max_age: 1h
  retry_base: 30s
  retry_max: 10m
  max_attempts: 5
  jitter: 10s
  scope: metrics
```

| Поле | Правило и значение по умолчанию |
| --- | --- |
| `metrics.endpoint` | Обязательно при наличии секции. Только `https`, с хостом, без userinfo, query и fragment. Путь сохраняется: `/select/0/prometheus/api/v1/query`. |
| `metrics.token_env` | Необязательно; **имя** переменной окружения по `^[A-Z_][A-Z0-9_]*$`. Значение токена читается только из окружения при запуске. |
| `metrics.timeout` | Положительная Go-длительность; `10s`. |
| `metrics.interval` | Положительная Go-длительность не больше `24h`; `60s`. Используется `metrics run`. |
| `alerts.state_db` | Обязательно при наличии секции. Путь к SQLite-базе `vpnctl`; родительский каталог должен существовать. |
| `alerts.grace` | Неотрицательная длительность; `5m`. `0` — `unknown` фиксируется на первом же unknown-семпле. |
| `alerts.flap_samples` | Целое `1..1000`; `2`. Число подряд идущих firing-семплов до `firing`. |
| `alerts.retention` | Положительная длительность; `24h`. Хранит состояние удалённого правила и доставленные/отменённые записи outbox. |
| `alerts.outbox_max_age` | Положительная длительность; `1h`. Максимальный возраст недоставленного уведомления. |
| `alerts.retry_base`, `alerts.retry_max` | Положительные длительности; `30s` и `10m`; `retry_max` не меньше `retry_base`. |
| `alerts.max_attempts` | `1..100`; `5`. Попыток доставки на одно уведомление. |
| `alerts.jitter` | Неотрицательная длительность; `10s`; не больше `metrics.interval`. Добавляется к интервалу случайно в `[0, jitter]`. |
| `alerts.scope` | `^[a-z][a-z0-9_.-]{0,31}$`; `metrics`. Метка области наблюдения в сообщении. |

Токены, chat ID и адреса серверов в конфигурацию и документацию не попадают.
В примерах используются RFC 5737/3849 и `example.com`.

## Состояния и переходы

Первое наблюдение правила фиксирует состояние сразу (`ok`, `firing` или
`unknown`). `firing` на первом же семпле отправляет уведомление: правило,
которое уже нарушено при запуске, не должно молчать.

| Из | В | Уведомление |
| --- | --- | --- |
| нет состояния | `firing` | `firing` |
| нет состояния | `ok` | нет |
| нет состояния | `unknown` | нет; ждёт смены состояния |
| `ok` | `firing` после `flap_samples` подряд | `firing` |
| `firing` | `ok` на первом семпле | `recovery` |
| `firing` | `unknown` после `grace` | `unknown` один раз |
| `ok` | `unknown` после `grace` | `unknown` один раз |
| `unknown` | `ok` | нет (это не recovery: `firing` не подтверждался) |
| `unknown` | `firing` после `flap_samples` | `firing` |
| любое | `ok` / `firing` / `unknown` без смены | нет |

Правило считается `unknown`, если запрос завершился ошибкой, вернул пустой
результат или `NaN`/`±Inf` (включая переполнение суммы). Пустой результат
**никогда** не превращается в `ok`, поэтому падение VictoriaMetrics или
недоступность узла не даёт ложного recovery.

До подтверждения переход хранится как `pending_state`/`pending_samples`/
`pending_since`; `since` и `last_change` меняются только при фактической смене
состояния. `decision` не делает запросов и полностью детерминирован при
заданных часах — это позволяет тестировать все переходы без сна и сети.

### Удалённые и переименованные правила

Если правило исчезло из файла, его последнее состояние сохраняется и один раз
отправляется уведомление `removed` (с `last_state`, значением и порогом). После
`retention` от момента исчезновения состояние удаляется. Переименование
выглядит как удаление старого имени и первое наблюдение нового: одно
`removed` и, если новое правило уже нарушено, одно `firing`. Второй экземпляр
воркера с другим набором правил не должен работать на той же базе: файл правил
— единственный источник состава.

## Outbox и доставка

Уведомление сначала записывается в `alert_outbox`, затем отправляется:

- одна транзакция фиксирует новое состояние и запись outbox; при сбое между
  записью и отправкой уведомление остаётся в очереди и будет отправлено после
  перезапуска;
- `attempts`, `next_attempt_at`, `claimed_until` и `expires_at` ограничивают
  повторы: экспоненциальный backoff от `retry_base` до `retry_max`, не больше
  `max_attempts` попыток и не дольше `outbox_max_age`;
- запись, у которой истёк `outbox_max_age`, помечается `abandoned_at` и больше
  не отправляется; она видна в `vpnctl alerts list` как `expired` и удаляется
  после `retention`;
- порядок сохраняется по правилу: запись не берётся, пока для того же правила
  есть более ранняя недоставленная запись (включая ожидающую backoff). Разные
  правила не блокируют друг друга;
- успешная отправка фиксируется только после ответа sink; при аварии между
  отправкой и фиксацией возможен повтор (at-least-once), но не молчаливая
  потеря firing/recovery;
- получатели — только операторы с ролью `admin` из `bot.operators`; конфигурация
  без admin отклоняется до первого цикла, viewer уведомлений не получает;
- дедупликация выполняется по `identity + fingerprint` (имя правила, событие,
  хэш меток и ревизия состояния), а не по тексту сообщения. Ключ попытки
  включает номер попытки, поэтому sink не подавляет повтор как дубликат;
- `alerts list` показывает `pending`/`expired` и до 20 открытых записей; этого
  достаточно, чтобы заметить недоставленный алерт.

Перезапуск читает сохранённое состояние: неизменившееся `firing` не отправляется
повторно, недоставленный outbox продолжает попытки.

## Mute

```sh
vpnctl alerts mute --config PATH --rule NAME [--until RFC3339]
```

Mute — это окно в `alert_mutes`, по умолчанию на 24 часа; `--until` должен быть
в будущем. Пока окно активно, переходы и состояние записываются как обычно, но
outbox-запись не создаётся: после окончания mute уже установленное `firing` не
пришлёт запоздавшее уведомление. `alerts list` печатает только активные окна.
Mute для ещё не наблюдавшегося правила допустим. `/mute` в боте не реализован.

## Сообщения и редактирование

Plain-text сообщение содержит:

```text
firing rule=node-cpu-busy severity=warning scope=metrics
state=firing value=95.5 condition=>= 90
labels=instance=exit-01,env=prod
observed_at=2026-01-02T03:04:05Z
```

- имя правила, severity, наблюдаемое значение, оператор и порог, метки,
  timestamp и scope;
- sink `notify.BotSink` не использует `parse_mode`, поэтому HTML-escape не
  нужен; управляющие символы (кроме перевода строки) заменяются пробелом, NUL
  невозможен;
- сообщение ограничено 1024 рунами до sink, sink дополнительно обрезает до
  лимита Telegram; метки ограничены 64 записями, ключ ≤128 и значение ≤256
  байт;
- в сообщение не попадают токены, выражения запросов, тела HTTP-ответов и
  сырые ошибки API: их просто нет в сохраняемом состоянии. Причина `unknown` —
  короткий токен (`no_data`, `non_finite`, `timeout`, `query_error`,
  `invalid_response`, `request_failed`), а не текст ошибки.

## CLI

```text
vpnctl metrics check --config PATH --rules PATH [--format text|json]
vpnctl metrics run --config PATH --rules PATH
vpnctl alerts list --config PATH [--format text|json]
vpnctl alerts mute --config PATH --rule NAME [--until RFC3339]
```

`metrics check` загружает конфигурацию и **все** правила, проверяет их
`ValidateRules` (при ошибке — ни одного запроса) и выполняет один цикл
вычислений без записи состояния и без отправки. `metrics run` открывает
state store, создаёт admin-sink из `bot.operators`, вычисляет сразу и затем с
интервалом `metrics.interval` + jitter; `SIGINT`/`SIGTERM` завершают цикл и
процесс с кодом 0. Обе команды требуют полный валидный файл конфигурации
(включая `panel`, `nodes`, `probe`, `bot`) — это общий строгий контракт
`vpnctl`, а не отдельная схема.

| Ситуация | Код |
| --- | --- |
| `check`: все правила `ok` | 0 |
| `check`: есть `firing` | 4 |
| `check`: нет `firing`, есть `unknown` | 5 |
| `run`: штатная остановка по сигналу | 0 |
| Неверные флаги, неизвестная подкоманда, отсутствие `--config`/`--rules` | 2 |
| Ошибка конфигурации, правил, токена, store, sink или цикла | 1 |

Ошибки конфигурации и правил перечисляют пути (`rules[0].comparison`,
`alerts.state_db`) и не повторяют значения токенов. `--format json` печатает
типизированные результаты/состояния; JSON-поля стабильны для чтения
оператором.

## Схема версии 4

Одна новая append-only миграция создаёт только новые таблицы; строки версий
1–3 (пробы, операции, Telegram offset) сохраняются без переклассификации:

- `alert_states` — по строке на правило: состояние, severity, сравнение,
  значение, порог, метки, fingerprint, `since`/`last_change`, `revision`,
  pending-поля и `missing_since`;
- `alert_outbox` — очередь с уникальным `dedupe_key`, счётчиком попыток,
  backoff, claim lease, `expires_at` и терминальными
  `delivered_at`/`abandoned_at`;
- `alert_mutes` — окна mute по правилу;
- `alert_runs` — одна строка с owner и lease единственного активного цикла.

Все таблицы `STRICT` и дополнительно ограничены `CHECK`; метки хранятся как
JSON и ограничены по размеру. Время — наносекунды UTC.

## Проверка и границы

Unit-тесты используют `httptest`-сервер с TLS на loopback и синтетические
значения/токены, fake-sink и временные SQLite-базы; часы передаются функцией,
sleep и реальная сеть не нужны. Покрыты все переходы, flap, grace, mute,
перезапуск, переименование и удаление, порядок и backoff outbox, истечение
срока, защита от второго экземпляра, дедупликация, редактирование и коды
выхода CLI.

```sh
make vpnctl-test
# либо, если Go уже установлен:
cd vpnctl
go test ./internal/alerts ./internal/store ./internal/config ./internal/cli
```

**Реальная runtime-приёмка не выполнялась.** Проверка с настоящей
VictoriaMetrics (роль из #57) и настоящим Bot API, включая сценарии «порог
нарушен → одно firing», «условие снято → одно recovery», остановку VM →
`unknown` без ложного recovery и возврат VM, требует одноразового стенда и
токена оператора. Она не входит в CI и в этот репозиторий; статические тесты и
`make vpnctl-test` не заменяют её.

## Ограничения и откат

- Нет истории значений и графиков, `/metrics`-команды, Alertmanager, paging,
  эскалаций и автоматической ремедиации.
- Один sink и один канал (admin-операторы из `bot.operators`); viewer алерты
  не получает.
- Гарантия доставки — at-least-once в пределах `outbox_max_age` и
  `max_attempts`; после исчерпания попыток запись остаётся `expired` для
  оператора, но автоматически не восстанавливается.
- Откат: остановить `vpnctl metrics run` и отменить squash-коммит отдельным PR.
  Таблицы версии 4 остаются в локальной базе; старый бинарник отклонит базу
  версии 4 как `ErrUnsupportedSchema`, поэтому нужна копия базы до обновления
  или совместимый бинарник.
