# Резервное копирование PostgreSQL панели

Роль `ansible/roles/cp_backup` и плейбуки `ansible/playbooks/backup.yml`,
`ansible/playbooks/restore.yml` реализуют задачу 2.3 архитектурного плана в
локальной части: зашифрованный `pg_dump`, хранение с ротацией, systemd-таймер
и учебное восстановление в одноразовую базу. **Копирование вне сервера не
реализовано** и остаётся отдельной задачей. Роль не применялась к рабочей панели;
проверка выполнялась только в одноразовом окружении (см. «Что проверено»).

## Контракт с панелью

Роль опирается на контракт роли `remnawave_panel` (issue #20): compose-проект
`remnawave`, сервис `postgres`. Контейнер находится по меткам
`com.docker.compose.project` и `com.docker.compose.service`; должен быть ровно
один работающий контейнер, иначе запуск завершается ошибкой. `pg_dump` и
`pg_restore --list` выполняются **внутри** этого контейнера через локальный
сокет, пароль базы роль не читает.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `cp_backup_recipients_file` | — (обязательна) | Путь на управляющей машине к файлу получателей age, вне Git-клона. |
| `cp_backup_compose_project` / `cp_backup_compose_service` | `remnawave` / `postgres` | Поиск контейнера по меткам compose. |
| `cp_backup_container` | пусто | Явное имя контейнера вместо поиска по меткам. |
| `cp_backup_db_name` / `cp_backup_db_user` | `postgres` / `postgres` | База и пользователь для `pg_dump`. |
| `cp_backup_dir` | `/var/lib/cp-backup` | Каталог артефактов (`0700`, root). |
| `cp_backup_keep_days` / `cp_backup_keep_count` | `14` / `30` | Ротация. |
| `cp_backup_on_calendar` | `*-*-* 03:15:00 UTC` | Расписание (`OnCalendar`). |
| `cp_backup_randomized_delay` | `30min` | `RandomizedDelaySec`. |
| `cp_backup_timer_enabled` | `true` | `false` останавливает и отключает таймер. |
| `cp_backup_unsafe_skip_verify` | `false` | Отключение проверки шифротекста; только явно и осознанно. |
| `cp_backup_age_install`, `cp_backup_age_version`, `cp_backup_age_sha256` | `true`, `v1.3.2`, SHA-256 | Установка закреплённого age. |

## Установка

```sh
.venv/bin/ansible-playbook -i <inventory> ansible/playbooks/backup.yml \
  -e cp_backup_recipients_file=/путь/вне/git/recipients.txt
```

По умолчанию плейбук применяется к группе `cp`; другую группу или хост задаёт
`-e cp_backup_hosts=<шаблон>` (например, exit при `cp_placement: exit`).
Роль устанавливает:

- `/usr/local/sbin/cp-backup` — скрипт резервного копирования;
- `/etc/cp-backup/recipients.txt` (`0640`) — только публичные получатели;
- `/etc/cp-backup/cp-backup.env` (`0640`) — несекретные настройки;
- `/etc/systemd/system/cp-backup.service` и `cp-backup.timer` — проверяются
  `systemd-analyze verify` при каждом применении роли;
- age из `/opt/age/<версия>` со ссылками в `/usr/local/bin`.

Разовый запуск вне расписания: `systemctl start cp-backup.service`, журнал:
`journalctl -u cp-backup.service`.

## Расписание и защита от наложения

Таймер `cp-backup.timer`: `OnCalendar` из переменной, `RandomizedDelaySec`,
`Persistent=true` (пропущенный при выключенном сервере запуск выполняется после
загрузки). Сервис `Type=oneshot` с `UMask=0077`, `RuntimeDirectory` (`0700`),
`ProtectSystem=full`, `ProtectHome`, `PrivateTmp`, `NoNewPrivileges`.
Скрипт берёт неблокирующий `flock` на `/run/lock/cp-backup.lock`: второй
одновременный запуск (таймер или ручной) завершается кодом `75` без изменений.
Unit-файлы и файл настроек не содержат секретов.

## Порядок одного запуска

1. Проверка настроек, блокировка, удаление собственных остатков
   `.cp-backup-*.partial` от аварийного запуска.
2. Файл получателей должен существовать, содержать хотя бы одного получателя и
   не содержать identity (`AGE-SECRET-KEY-`), иначе — ошибка.
3. `docker exec <контейнер> pg_dump --format=custom | age --encrypt` во
   временный файл в каталоге артефактов; `set -o pipefail`, любой ненулевой код
   завершает запуск.
4. `fsync` временного файла, затем проверка шифротекста:
   `age --decrypt | pg_restore --list` (ненулевой код или пустое оглавление —
   ошибка).
5. Атомарный `rename` в итоговое имя и `fsync` каталога.
6. Ротация.

При любой ошибке временный файл удаляется, существующие артефакты не меняются.
В журнал пишутся только пути, размеры, количество записей оглавления и SHA-256.

### Проверка шифротекста без ключа оператора на сервере

Identity оператора на сервер **не копируется**. Для проверки каждый запуск
создаёт одноразовую пару age в `RuntimeDirectory` (tmpfs, `0700`), добавляет её
публичный ключ как дополнительного получателя, расшифровывает временный файл
этим ключом и удаляет его при выходе. Поэтому заголовок артефакта содержит на
одного получателя больше, чем файл получателей; расшифровать его после запуска
может только оператор. Альтернатива — переменная окружения
`CP_BACKUP_VERIFY_IDENTITY_FILE` (identity, которой зашифрован артефакт); она
нужна для проверки отказа identity и не задаётся ролью. Флаг
`cp_backup_unsafe_skip_verify: true` отключает проверку и пишет предупреждение в
журнал; в тестах он не используется.

## Имена и ротация

Имя артефакта: `cp-backup-<UTC YYYYmmddTHHMMSSZ>.pgcustom.age` (`pgcustom` —
формат `pg_dump -Fc`). Существующий файл с тем же именем не перезаписывается.
Ротация выполняется только после успешного проверенного запуска и затрагивает
только файлы, имя которых совпадает с этим шаблоном; прочие файлы в каталоге не
трогаются. Новейший артефакт сохраняется всегда, независимо от возраста; из
остальных удаляются те, что старше `cp_backup_keep_days` (по времени в имени)
или выходят за `cp_backup_keep_count`. Неудачный запуск ротацию не выполняет.

## Хранение ключей

- Identity age (`AGE-SECRET-KEY-…`) хранится только у оператора вне сервера и
  вне Git (например, офлайн-носитель или менеджер паролей). Потеря identity
  означает потерю всех резервных копий.
- На сервер попадает только файл получателей (публичные ключи). Можно указать
  несколько получателей — например, основной и резервный ключ оператора.
- Ротация ключа: добавьте новый публичный ключ, примените роль, после первой
  копии с новым ключом удалите старый получатель. Старые артефакты остаются
  зашифрованы старым ключом; храните его, пока они нужны.
- Роль отказывается работать, если файл получателей лежит внутри Git-клона или
  содержит identity.

## Учебное восстановление

`restore.yml` восстанавливает выбранный артефакт в **новую** базу на
одноразовом PostgreSQL (отдельный контейнер на чистой VM или на хосте учений):

```sh
.venv/bin/ansible-playbook -i <inventory> ansible/playbooks/restore.yml \
  -e cp_restore_hosts=<хост-учений> -e cp_restore_confirm=true \
  -e cp_restore_artifact_src=/путь/cp-backup-YYYYmmddTHHMMSSZ.pgcustom.age \
  -e cp_restore_identity_file=/путь/вне/git/identity.txt \
  -e cp_restore_container=<одноразовый-postgres> \
  -e cp_restore_db_name=panel_restore
```

- Без `cp_restore_confirm: true` плейбук ничего не делает.
- Артефакт и identity берутся с управляющей машины, копируются во временный
  каталог `0700` на хосте учений (identity — с `no_log`) и удаляются в блоке
  `always` даже при ошибке.
- Восстановление: `createdb`, затем `age --decrypt | pg_restore --exit-on-error
  --single-transaction --no-owner --no-acl`. При ошибке созданная база удаляется.
- Отказ без `cp_restore_replace: true`: база с таким именем уже существует или
  контейнер принадлежит живому compose-проекту панели (`cp_restore_live_project`,
  по умолчанию `remnawave`). С `cp_restore_replace: true` существующая база
  удаляется (`dropdb --force`) до восстановления — для живой панели это
  разрушительно и в учениях не используется.
- После восстановления проверяется, что в базе есть таблицы, и, если задано,
  число строк контрольной таблицы: `cp_restore_sentinel_table`,
  `cp_restore_sentinel_rows`.

### Контрольная таблица учений

Учения `ansible/roles/cp_backup/tests/drill.sh` создают базу `panel` с таблицей
`public.cp_backup_sentinel (id integer PRIMARY KEY, label text NOT NULL)` и
**42** строками `(n, 'row-n')`. После восстановления сравниваются число строк и
MD5 от упорядоченного содержимого с исходной фикстурой.

Скрипт учений запускается от root только в одноразовом окружении с Docker и
сетью (GitHub, Docker Hub), после `make bootstrap && make -C ansible bootstrap`.
Он поднимает два одноразовых контейнера `postgres:17.6-alpine`, генерирует
одноразовую identity, применяет роль к локальному хосту и проверяет:
`systemd-analyze verify`, резервную копию с проверкой, `age -d | pg_restore
--list` ключом оператора, блокировку второго одновременного запуска, ротацию,
отказы (несуществующая база, чужая и отсутствующая identity, пустой файл
получателей, identity в файле получателей, остановленный контейнер) с
неизменными прежними артефактами, отказы `restore.yml` и восстановление после
переименования исходной базы. Без systemd в роли PID 1 включение таймера
пропускается (`--skip-tags cp_backup_systemd`). Никогда не запускайте его на
сервере панели.

## Отказы и диагностика

| Симптом в журнале | Причина и действие |
| --- | --- |
| `another run holds … refusing to overlap`, код 75 | Идёт другой запуск; дождитесь его. |
| `expected one running remnawave/postgres container, found N` | Панель остановлена или контейнеров несколько; проверьте compose или задайте `cp_backup_container`. |
| Ошибка `pg_dump` | База недоступна или неверное имя; прежние копии не изменены. |
| `recipients file … lists no recipients` / `contains an age identity` | Исправьте файл получателей на управляющей машине и примените роль. |
| Ошибка `age --decrypt` или `pg_restore --list` | Повреждённый вывод или сбой age; новая копия отброшена, прежние не изменены. |
| `artifact … already exists` | Совпадение секунды запуска; повторите запуск. |
| Заполнен диск | Запуск завершится ошибкой без частичного файла; уменьшите хранение или освободите место. |

Неудачный запуск переводит `cp-backup.service` в состояние `failed`; следите за
ним через `systemctl --failed` или мониторинг.

## Откат

1. Отключите таймер: примените роль с `-e cp_backup_timer_enabled=false` или
   выполните `systemctl disable --now cp-backup.timer`.
2. Существующие артефакты в `cp_backup_dir` остаются; удалять их не требуется.
3. Изменение репозитория откатывается отдельным PR, отменяющим squash-коммит.

## Что проверено и что нет

Проверено учениями в одноразовом контейнере Ubuntu 24.04 (root) с Docker и
одноразовыми контейнерами PostgreSQL 17.6, без рабочей панели и реальных ключей.
Не проверено: запуск сервиса и таймера под настоящим systemd (в окружении учений
systemd не был PID 1, проверялись только `systemd-analyze verify` и прямой
запуск скрипта с теми же настройками), работа с реальным compose-стеком
Remnawave из #20 и копирование вне сервера (не реализовано).

## Происхождение age

Закреплён `age v1.3.2` с GitHub Releases `FiloSottile/age`. SHA-256 архивов
`linux-amd64` и `linux-arm64` в `defaults/main.yml` совпадают с digest, который
публикует GitHub, а сами архивы проверены их Sigsum-доказательствами
(`sigsum-verify v0.13.1`, политика `sigsum-generic-2025-1`, ключи из
`SIGSUM.md` проекта age). При обновлении версии повторите эту проверку и
обновите оба значения.
