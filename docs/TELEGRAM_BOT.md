# Telegram-бот vpnctl

`vpnctl bot` — read-only Telegram-бот из задач 5.3 и 5.4
[архитектурного плана](ARCHITECTURE_PLAN.md) и решения D-010
([реестр решений](DECISIONS.md)). Allowlisted-оператор проверяет состояние
панели и узлов из Telegram без shell и SSH. Бот не меняет панель: методов
записи у клиента панели нет. Приём вебхуков панели (задача 5.5), контейнерная
роль (5.6) и опасные команды с подтверждением в эту поставку не входят.

Процесс также предоставляет интерфейс `notify.Sink` для будущих алертов;
источника событий, который бы его вызывал, в этой поставке нет.

## Запуск

```sh
vpnctl bot --config PATH
```

- Поддерживается только long polling. Webhook-сервера, TLS-листенера и
  публичного входящего порта нет.
- На старте выполняется `getMe`; неверный токен или конфигурация завершают
  процесс до первого `getUpdates`.
- `SIGINT`/`SIGTERM` отменяют текущий poll; процесс завершает текущую запись
  offset, закрывает SQLite-базу и выходит с кодом 0.
- Ошибка запуска или типизированная ошибка Telegram (например, `401`) — код 1.
- `getMe` и одна попытка `sendMessage` ограничены `15s`; `getUpdates` —
  `timeout + 15s`. Сеть не может подвесить процесс навсегда.
- Токены читаются только из переменных окружения, названных в
  `panel.token_env` и `bot.token_env`. Значения не печатаются, не логируются и
  не попадают в сообщения об ошибках.

HTTP-клиент — стандартная библиотека Go; дополнительных зависимостей нет.
`api.telegram.org` используется по умолчанию. Бот ходит в Telegram и панель
только по HTTPS; `http` разрешён лишь для loopback-адреса self-hosted Bot API
или тестового fake API.

## Конфигурация

Секция `bot` обязательна — как `panel`, `nodes` и `probe`; `config validate`
проверяет её так же строго. Синтетический пример — в
[config.example.yaml](../vpnctl/config.example.yaml).

```yaml
bot:
  token_env: VPNCTL_BOT_TOKEN
  state_db: /var/lib/vpnctl/state.db
  # api_base: http://127.0.0.1:8081
  operators:
    - id: 100000001
      role: admin
    - id: 100000002
      role: viewer
  chat_ids: [-1000000000001]
```

| Поле | Правило |
| --- | --- |
| `bot` | Обязательно. |
| `bot.token_env` | Обязательно; имя переменной окружения по `^[A-Z_][A-Z0-9_]*$`, не сам токен. |
| `bot.api_base` | Необязательно. По умолчанию `https://api.telegram.org`. `https` с хостом, без userinfo, query, fragment и пути; `http` — только для loopback-хоста (`127.0.0.0/8`, `::1`, `localhost`). |
| `bot.state_db` | Обязательно; путь к SQLite-базе `vpnctl`. Родительский каталог должен существовать. |
| `bot.operators` | Обязательно; непустой список. |
| `bot.operators[].id` | Обязательный положительный числовой Telegram user ID, уникальный в списке. |
| `bot.operators[].role` | `admin` или `viewer`. Обе роли в этой поставке имеют одинаковый read-only набор команд; различие нужно для будущих задач и для получателей алертов. |
| `bot.chat_ids` | Необязательно; ненулевые уникальные Telegram chat ID. Чаты из списка разрешены дополнительно к private. |

`bot.token_env` не может содержать значение токена: шаблон имени отвергает
строчные буквы, `-` и `.`. Поле `token` в схеме отсутствует и как неизвестное
отклоняется. Ошибки не повторяют значения токенов, chat ID и содержимое чатов.

## Allowlist и чаты

- Отправитель должен быть в `bot.operators`; иначе ответа нет, содержимое
  сообщения не повторяется. Обновление потребляется (offset сдвигается) и
  учитывается в счётчике `ignored_updates`, но сообщение не отправляется.
- Private-чат разрешён всегда, если отправитель в allowlist. Групповой,
  supergroup- или канальный чат — только если его ID явно указан в
  `bot.chat_ids`; по умолчанию в группах бот молчит. Отправитель в разрешённой
  группе всё равно должен быть в allowlist.
- Обновление без текста, без `from`/`chat`, изменённое сообщение (в запросе
  только `message`) и сообщение от бота безопасно игнорируются и потребляются.
- Счётчик игнорированных обновлений пишется в итоговый лог (`ignored_updates`);
  sender/chat ID и текст в лог не попадают.

## Команды

| Команда | Аргументы | Ответ |
| --- | --- | --- |
| `/help` | нет | Список команд и роль отправителя. |
| `/status` | нет | Доступность панели и сводка: всего узлов, `connected`, `connecting`, `disconnected`, `disabled`. |
| `/nodes` | нет | До `20` узлов: имя, country code, статус, `usersOnline`, трафик (used/limit), время последнего изменения. Если узлов больше — строка «… ещё N узлов». |
| `/users` | нет | `total` панели и число пользователей на одной странице (`100`, смещение 0), плюс счётчики `ACTIVE`, `DISABLED`, `LIMITED`, `EXPIRED` и неизвестных статусов. |
| `/user <id>` | ровно один положительный числовой ID | Username, статус, трафик (`used`/`limit`, за всё время), `OnlineAt` и `FirstConnectedAt`. |

- Лишние аргументы, нечисловой, нулевой или отрицательный ID и неизвестная
  команда дают одну короткую строку использования. Аргументы и текст команды
  не повторяются в ответе.
- `/user` показывает только поля, которые уже отдаёт read-only клиент панели.
  `expireAt` и UUID в ответ не выводятся.
- Ответы — plain text без `parse_mode`, поэтому HTML-экранирование не нужно и
  некорректный HTML не отправляется.
- Один ответ ограничен `4096` UTF-16 code units (лимит Telegram). Более
  длинный текст обрезается с явным маркером `… (сокращено)`; `/nodes` и
  `/users` ограничены и по числу строк/странице.
- Не выводятся: ссылки подписки, UUID, пароли и токены, адреса узлов, прокси-URL
  и сырые тела ответов API. `vpnctl` вообще не декодирует секретные поля
  моделей панели.

## Ошибки

| Источник | Поведение |
| --- | --- |
| Панель `401`, `403`, `404`, `429`, `5xx`, транспорт, таймаут | Короткое сообщение оператору: «Панель: ошибка авторизации (401)», «Панель: ошибка сервера (5xx)», «Панель: недоступна» и т. п. Тело, `errorCode` и URL в ответ и лог не попадают. |
| Telegram `getUpdates` `429` | Ожидание `retry_after`, но не больше `30s`, затем следующий poll. |
| Telegram `sendMessage` `429` | Ожидание `retry_after` (не больше `30s`) и одна повторная попытка; затем ошибка возвращается. |
| Telegram `getUpdates` `401` или `sendMessage` `401` | Процесс останавливается с типизированной ошибкой (`telegram.ErrUnauthorized`). |
| Прочие ошибки poll | Экспоненциальная пауза `1s → 2s → … → 30s` до отмены контекста; без плотного цикла и без бесконечного повтора внутри одного запроса. |
| Ошибка SQLite при записи offset | Процесс останавливается с ошибкой, а не повторяет claim в плотном цикле: offset — единственный курсор, сбой базы требует внимания оператора. |

## Offset и дедупликация

Состояние хранится в принятом SQLite-хранилище
([STATE_STORE.md](STATE_STORE.md)), схема версии 2:

- `telegram_offsets` — один ряд с `update_offset` (следующий offset для
  `getUpdates`);
- `telegram_updates` — обработанные `update_id`, не более последних `1024`.

`ClaimBotUpdate` в одной транзакции `BEGIN IMMEDIATE` вставляет `update_id` и
монотонно поднимает offset до `update_id + 1`. Поэтому:

- повторный `update_id` в одном батче или после перезапуска не отвечается
  второй раз;
- два процесса на одной базе не откатывают offset назад и не отвечают на одно
  обновление дважды;
- перезапуск продолжает с сохранённого offset, старые команды не воспроизводятся.

Обновление сначала фиксируется в базе, затем обрабатывается. Это гарантирует
«не более одного ответа»; при аварии между записью и отправкой команда теряется,
а не отвечается повторно. Offset также сдвигается для дубликатов, поэтому
повторно присланный старый батч не зацикливает poll.

## Sink уведомлений

`vpnctl/internal/notify`:

```go
type Sink interface {
    Send(ctx context.Context, alert Alert) error
}

type Alert struct {
    ID        string   // стабильная идентичность условия
    Severity  Severity // info, warning, critical
    Message   string
    DedupeKey string   // пусто → ID
}
```

`notify.NewAdminSink(sender, operators)` фильтрует операторов с `role: admin`
и создаёт `notify.BotSink`, который отправляет им plain-text сообщения; viewer
в получатели не попадают. `NewBotSink` принимает готовый список chat ID, если
источник алертов не использует конфигурацию операторов.

`BotSink`:

- дедупликация по ключу в окне `5m`; ключ освобождается при ошибке доставки,
  поэтому вызывающий может повторить;
- не более `32` одновременных доставок; сверх лимита — `ErrQueueFull`, без
  неограниченной очереди;
- минимальный интервал между отправками `1s`; если ожидание больше `5s` —
  `ErrRateLimited`;
- ошибки доставки возвращаются вызывающему (`errors.Join` по получателям), не
  проглатываются; текст обрезается до лимита Telegram;
- кэш дедупликации ограничен по числу ключей.

Sink — библиотечный контракт для задачи 5.5 и других будущих источников; в
`vpnctl bot` он пока не подключён ни к какому событию.

## Проверка

```sh
make vpnctl-test          # gofmt, go vet, go test ./...
cd vpnctl && go test ./internal/telegram ./internal/bot ./internal/notify
```

Тесты не обращаются к Telegram и не используют реальные токены:

- `internal/telegram` — fake Bot API на loopback HTTP: пути `/bot<token>/...`,
  заголовки, `offset`/`limit`/`timeout`, `allowed_updates: ["message"]`, plain
  text без `parse_mode`, лимит `4096`, отказ от редиректов, `400/401/403/404/429/5xx`,
  `retry_after`, транспортные ошибки без токена и URL, лимит тела.
- `internal/bot` — allowlist, роли, чаты, разбор команд, ошибки панели,
  ограничение `/nodes` и `/users`, отсутствие UUID/секретов, дедупликацию,
  перезапуск с сохранённым offset, отмену, `429`/`401`, ошибки записи offset.
- `internal/notify` — дедупликация и её окно, граница очереди, rate limit,
  частичный отказ и повтор, отмена, валидация, фильтрация admin-получателей.
- `internal/store` — миграция версии 1 → 2 с сохранением данных, монотонность
  offset, конкурентные claim (ровно один победитель), retention.

### Scripted runtime proof

Проверка выполнялась собранным бинарником (`CGO_ENABLED=0 go build`) против
fake Bot API на loopback HTTP и fake панели на локальном HTTPS с одноразовым
самоподписанным сертификатом (`SSL_CERT_FILE`). Все токены, ID, имена и адреса
синтетические; скрипт и артефакты не входят в репозиторий.

Наблюдаемый результат:

- первый запуск: `getMe` → 8 ответов на `/help`, `/status`, `/nodes`, `/users`,
  `/user 42`, `/user abc`, `/unknown` и `/help` viewer; unknown sender и группа
  проигнорированы (`ignored_updates=2`); дубликат `update_id 1010` отвечен один
  раз; `allowed_updates=["message"]`; offset после запуска — `1011`;
- `SIGTERM` → код 0, `bot stopped`, база закрыта;
- второй запуск: первый `getUpdates` с offset `1011`, fake API повторно прислал
  весь старый батч — новых ответов нет (8 → 8), offset остался `1011`;
- в ответах нет UUID, адресов, токенов, имён секретных полей и сырых тел.

Проверка с реальным ботом требует операторского токена, выполняется отдельно и
не входит в CI или репозиторий. В этой поставке она не выполнялась.

## Ограничения и откат

- Нет команд изменения, подтверждений опасных операций, inline-режима, медиа,
  администрирования групп, webhook, нескольких ботов, `/why`, `/probe`,
  `/metrics`, `/mute`, upstream-команд и deployment-роли.
- Откат: остановить процесс и отменить squash-коммит отдельным PR. Внешнее
  состояние не меняется; SQLite-база содержит только offset и обработанные
  `update_id` и игнорируется Git (`*.db`, `*.sqlite*`).
