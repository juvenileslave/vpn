# Хранилище состояния vpnctl

Пакет `vpnctl/internal/store` — локальное SQLite-хранилище из задачи 5.2
[архитектурного плана](ARCHITECTURE_PLAN.md): история проб, метаданные
возобновляемых операций и состояние Telegram-бота (offset и обработанные
`update_id`). Это библиотека без собственной команды CLI. Пакет используют
`vpnctl bot` и тесты; воркер, планировщик, очередь и облачная оркестрация (в том
числе смена IP) здесь не реализованы. Версии конфигов апстримов из пункта 5.2 в
эту поставку не входят.

## Драйвер и подключение

- `database/sql` + `modernc.org/sqlite` v1.62.0 — чистый Go, CGO не нужен
  (`CGO_ENABLED=0 go build` работает).
- DSN собирается из абсолютного пути как SQLite URI `file:<путь>?...`. Путь
  экранируется (`?`, `#`, `%` и т. п. остаются частью имени файла), поэтому через
  путь нельзя добавить параметры DSN или `PRAGMA`.
- Параметры соединения:

  | Параметр | Значение | Зачем |
  | --- | --- | --- |
  | `mode=rw` | файл не создаётся самим SQLite | создание выполняет `Open` с правами `0600` |
  | `busy_timeout` | 5000 мс (`store.BusyTimeout`) | ограниченное ожидание блокировки другого процесса |
  | `foreign_keys` | `1` | включено для всех будущих связей |
  | `synchronous` | `FULL` | подтверждённая запись переживает сбой питания |
  | `_txlock` | `immediate` | транзакция сразу берёт блокировку записи |
  | `journal_mode` | `WAL` | читатели не блокируют писателя; задаётся только после проверки, что файл принадлежит vpnctl |

- В пуле ровно одно соединение (`SetMaxOpenConns(1)`): методы `Store`
  безопасны для горутин и выполняются последовательно.
- WAL рассчитан на локальную файловую систему. Не размещайте базу на NFS/SMB
  и в синхронизируемых каталогах.

## API

```go
s, err := store.Open(ctx, path) // создаёт файл 0600 или открывает существующий
defer s.Close()

rec, err := s.AppendProbe(ctx, store.ProbeRecord{...})   // rec.ID назначен хранилищем
recs, err := s.LatestProbes(ctx, "exit-01", 20)          // 1..store.MaxLimit (1000)

op, err := s.CreateOperation(ctx, "rotate_ip", "")       // pending, revision 1
op, err = s.GetOperation(ctx, op.ID)
op, err = s.UpdateOperation(ctx, op.ID, op.Revision, store.StateRunning, "create_ip")

offset, err := s.BotOffset(ctx)                          // 0, если бот ещё не работал
claimed, err := s.ClaimBotUpdate(ctx, 12345)             // false для дубликата
```

Все чтения и записи принимают `context.Context`; отменённый контекст прерывает
запрос, незавершённая транзакция откатывается. Методы возвращают ошибки и не
паникуют на входных данных или сбоях базы.

### Пробы

`ProbeRecord`: `ID`, `Target`, `Stage`, `Family`, `Outcome`, `ObservedAt`,
`Duration`, `Bytes`, `ErrorCode`. Тип принадлежит пакету store и не зависит от
будущего пакета проб.

| Поле | Правило |
| --- | --- |
| `Target` | метка цели (например, имя узла), `^[A-Za-z0-9]([A-Za-z0-9._-]{0,61}[A-Za-z0-9])?$`; не URL и не адрес с учётными данными |
| `Stage` | `^[a-z][a-z0-9_]{0,31}$`, например `tcp`, `tls`, `http` |
| `Family` | `ipv4` или `ipv6` |
| `Outcome` | `success`, `failure` или `timeout` |
| `ObservedAt` | от Unix epoch до 2262 года; хранится в наносекундах UTC |
| `Duration`, `Bytes` | неотрицательные |
| `ErrorCode` | для `success` пусто; иначе обязательно, `^[a-z][a-z0-9_]{0,63}$` |

`ErrorCode` — короткий код, а не текст ошибки: строки вида
`dial tcp ...: connection refused`, тела HTTP-ответов, учётные данные и
содержимое конфигурации не проходят проверку и не сохраняются. Сообщения об
ошибках проверки не повторяют отклонённое значение.

`LatestProbes` возвращает записи цели от новых к старым: `ObservedAt` по
убыванию, при равенстве — `ID` по убыванию. Лимит вне 1..1000 —
`ErrInvalidArgument`.

### Операции

`Operation`: `ID` (32 hex-символа, случайный), `Kind`, `State`, `Step`,
`Revision`, `CreatedAt`, `UpdatedAt`. `Kind` и `Step` — токены
`^[a-z][a-z0-9_]{0,31}$`, `Step` может быть пустым. Параметры и результаты
операций не хранятся.

Переходы:

```text
pending ──► running ──► succeeded
              │  ▲  └──► failed
              └──┘ (смена step)
```

- `pending → running`;
- `running → running` только с другим `Step`;
- `running → succeeded | failed`;
- из `succeeded` и `failed` переходов нет.

`UpdateOperation(ctx, id, expectedRevision, next, step)` — compare-and-swap в
одной транзакции `BEGIN IMMEDIATE`: строка читается и обновляется под
блокировкой записи, `UPDATE ... WHERE id = ? AND revision = ?` дополнительно
защищает от гонки. Успешное обновление увеличивает `Revision` ровно на 1.
Любая ошибка оставляет строку без изменений.

### Состояние Telegram-бота

`BotOffset(ctx)` возвращает текущий `update_offset` или `0`, если бот ещё не
обработал ни одного обновления.

`ClaimBotUpdate(ctx, updateID)` — атомарная операция в одной транзакции
`BEGIN IMMEDIATE`:

1. вставляет `updateID` в `telegram_updates`; конфликт означает дубликат —
   операция возвращает `false` без изменений;
2. монотонно поднимает `telegram_offsets.update_offset` до `updateID + 1`
   (`max`), поэтому два процесса не откатывают offset и не отвечают на одно
   обновление дважды;
3. удаляет старые `update_id`, оставляя последние `1024`; offset уже находится
   дальше них, и `getUpdates` их не вернёт.

`updateID` должен быть положительным и меньше `math.MaxInt64`; иначе
`ErrInvalidArgument`. После перезапуска бот продолжает с сохранённого offset.
Семантика доставки — не более одного ответа на обновление: запись фиксируется
до отправки ответа.

## Ошибки

Проверяйте через `errors.Is`:

| Ошибка | Когда |
| --- | --- |
| `ErrNotFound` | операции с таким ID нет |
| `ErrConflict` | `expectedRevision` не совпадает с текущей ревизией (устаревший писатель) |
| `ErrTerminal` | операция уже `succeeded` или `failed` |
| `ErrInvalidTransition` | переход не разрешён машиной состояний |
| `ErrInvalidArgument` | неверный ввод: путь, лимит, метка, токен, ID, ревизия |
| `ErrNotDatabase` | файл не является читаемой базой SQLite |
| `ErrForeignDatabase` | база SQLite создана не vpnctl (чужой `application_id` или непустая схема без него) |
| `ErrUnsupportedSchema` | версия схемы новее поддерживаемой этой сборкой |
| `ErrCorrupt` | сохранённая строка нарушает контракт записи |
| `ErrOrphanedSidecar` | основного файла нет, но рядом уже есть `-wal`, `-shm` или `-journal` |

Порядок проверок в `UpdateOperation`: существование → ревизия → терминальное
состояние → допустимость перехода.

## Схема и миграции

Версия схемы хранится в `PRAGMA user_version`, принадлежность файла — в
`PRAGMA application_id = 0x76706e63` (`vpnc`). Текущая версия — 2.

```text
probes(id INTEGER PK AUTOINCREMENT, target, stage, family, outcome,
       observed_at INTEGER ns UTC, duration_ns, bytes, error_code)  STRICT
  index probes_target_latest(target, observed_at DESC, id DESC)
operations(id TEXT PK, kind, state, step, revision >= 1,
           created_at INTEGER ns UTC, updated_at INTEGER ns UTC)    STRICT
telegram_offsets(id INTEGER PK CHECK (id = 1), update_offset >= 0)  STRICT
telegram_updates(update_id INTEGER PK > 0)                          STRICT
```

Версия 2 добавляет `telegram_offsets` и `telegram_updates`; существующие базы
версии 1 мигрируют без потери данных, потому что миграция только создаёт новые
таблицы.

Столбцы дополнительно ограничены `CHECK` (допустимые значения и длины).

- Каждая миграция и запись новой `user_version` выполняются в одной транзакции:
  при ошибке откатываются и DDL, и изменения данных, версия остаётся прежней.
- Версия перечитывается внутри транзакции, поэтому два процесса, одновременно
  открывающие базу, не применят миграцию дважды.
- Миграции только добавляются в конец списка; выпущенные не редактируются.
- База с версией новее поддерживаемой отклоняется (`ErrUnsupportedSchema`) без
  изменений: откат бинарника не может открыть базу, обновлённую новой версией.

### Существующие файлы и владение при ошибке

`Open` создаёт отсутствующий файл эксклюзивно (`O_EXCL`) с правами `0600`;
родительский каталог должен существовать. Уже отменённый контекст отклоняется
до любых действий с файловой системой.

`Open` удаляет только то, что создал сам:

- Если основного файла нет, а `-wal`, `-shm` или `-journal` уже существует,
  новая база не создаётся: `ErrOrphanedSidecar`, ни один файл не меняется.
  Такой файл принадлежит кому-то другому, а SQLite мог бы применить или удалить
  его при открытии новой базы. Проверка повторяется сразу после эксклюзивного
  создания, чтобы закрыть окно гонки.
- Если инициализация новой базы не удалась, основной файл удаляется, только
  пока это тот же inode, который создал этот вызов (`os.SameFile`); затем
  удаляются sidecar-файлы, которых до создания не было и которые, значит,
  создал SQLite для этой базы. Подменённый файл не трогается.
- Существующий файл и его sidecar-файлы никогда не удаляются и не
  перезаписываются кодом пакета: посторонний файл, чужая база SQLite или
  слишком новая схема дают ошибку до любой записи, а `journal_mode` меняется
  только после проверки принадлежности. Права существующего файла не меняются.
  `-wal`/`-journal` существующей базы — её файлы восстановления; их обрабатывает
  сам SQLite по своему протоколу (откат горячего журнала, checkpoint WAL), так
  что зафиксированные данные сохраняются.

Ограничение: одновременное первое открытие одного нового пути несколькими
процессами, один из которых завершается ошибкой, может удалить файл, ещё
используемый другим. Первое создание базы выполняйте одним процессом.

## Резервное копирование

- В режиме WAL подтверждённые данные могут находиться в файле `<база>-wal`.
  Копирование одного основного файла во время работы может дать неполную или
  несогласованную копию.
- Безопасные варианты: копировать при закрытом хранилище (при закрытии
  последнего соединения SQLite переносит WAL в основной файл), либо снимать
  копию средствами SQLite (`VACUUM INTO '<файл>'` или `sqlite3 <база>
  ".backup <файл>"`).
- Копия содержит только метки целей, коды ошибок и метаданные операций, но
  раскрывает топологию и историю доступности: храните её с правами `0600` и не
  добавляйте в Git (`*.db`, `*.sqlite*` уже в `.gitignore`).
- Восстановление из старой копии возвращает старые ревизии операций;
  возобновление по ним должно учитывать внешнее состояние.

## Проверка

Тесты используют настоящие временные базы SQLite в `t.TempDir()` — без моков и
без проверок текста SQL — и покрывают: сохранение после закрытия и повторного
открытия, изоляцию баз, порядок и лимиты проб, отсутствующие ID, откат
неудачной миграции, миграцию версии 1 → 2 с сохранением строк, отклонение
устаревшей ревизии, конкурирующих писателей (одна успешная запись),
неизменность терминальных состояний, монотонность bot offset, одновременный
claim одного `update_id` (ровно один победитель), retention обработанных ID,
посторонние и повреждённые файлы, сохранение чужих `-wal`/`-shm`/`-journal` при
неудачном открытии (в том числе с отменённым контекстом), инъекцию параметров
через путь.

```sh
cd vpnctl
go test -v ./internal/store
go test -race ./internal/store   # нужен CGO и C-компилятор для race detector
go vet ./internal/store
```
