# Секреты: SOPS + age

Документ описывает репозиторную часть этапа 0.2
[архитектурного плана](ARCHITECTURE_PLAN.md): правила `.sops.yaml`, порядок работы
оператора и офлайн-проверку индекса Git. **Зашифрованные секреты в этом
репозитории не публикуются**, ключ оператора и значения секретов хранятся вне
Git. Плейбуки, роли и `community.sops` здесь не реализованы.

## Что есть в репозитории

| Файл | Назначение |
| --- | --- |
| `.sops.yaml` | `creation_rules` для `secrets/*.sops.yaml` и `secrets/*.sops.yml`, `encrypted_regex`, пустой список получателей age |
| `.gitignore` | игнорирует `secrets/`, `*.agekey`, `age-keys.txt`, `.env` и `.env.*`, кроме `.env.example` |
| `scripts/check_secrets.py` | pre-commit hook `secret-material`, запускается в `make check` |
| `scripts/tests/test_check_secrets.py` | unit-тесты проверки на временных Git-репозиториях |

Требуемые инструменты оператора: `sops` и `age` (`age-keygen`). Поведение ниже
проверено локально с sops 3.11.0 и 3.13.3 и age 1.2.1 на одноразовых ключах.

## Ключ оператора и хранение

Ключ создаётся на управляющей машине, вне рабочего клона:

```sh
mkdir -p ~/.config/sops/age
umask 077
age-keygen -o ~/.config/sops/age/keys.txt
age-keygen -y ~/.config/sops/age/keys.txt   # публичный получатель age1...
```

`~/.config/sops/age/keys.txt` — путь, который sops читает по умолчанию на Linux;
другой путь задаётся через `SOPS_AGE_KEY_FILE`. Правила хранения:

- закрытый ключ (строка с префиксом `AGE-SECRET-KEY-`) не копируется в репозиторий,
  issue, PR, чаты, логи и облачные заметки;
- резервная копия — офлайн (зашифрованный носитель или менеджер паролей) у
  владельца; лучше завести второй, резервный ключ и добавить его получателем;
- публичный получатель `age1...` секретом не является, но в этот публичный
  репозиторий не добавляется, пока владелец явно не решит иначе.

## Включение шифрования оператором

`.sops.yaml` намеренно поставляется с `age: []`. В этом состоянии `sops -e`
завершается с ошибкой `Could not generate data key: [empty key group provided]`
(код 1, вывод пуст) и не создаёт файл, который никто не сможет расшифровать.

Оператор меняет локально ровно одну строку:

```diff
-    age: []
+    age: [age1<основной_получатель>, age1<резервный_получатель>]
```

Это изменение не коммитится: перед `git add` проверьте, что `.sops.yaml` не
изменён (`git diff -- .sops.yaml`).

## Шифрование и расшифровка

`path_regex` срабатывает для `secrets/<имя>.sops.yaml` и `secrets/<имя>.sops.yml`
(относительный или абсолютный путь). Файлы в других местах не шифруются
правилом: sops сообщит `no matching creation rules found`.

```sh
mkdir -p secrets
sops edit secrets/panel.sops.yaml          # создать или изменить в $EDITOR
sops -e -i secrets/panel.sops.yaml         # зашифровать существующий открытый файл
sops -d secrets/panel.sops.yaml            # расшифровать в stdout
sops -d --extract '["db_password"]' secrets/panel.sops.yaml
```

Расшифрованные данные не записывайте в файлы рабочего клона.

`encrypted_regex` шифрует значения ключей, имя которых без учёта регистра
содержит `password`, `passwd`, `secret`, `token`, `key`, `credential`,
`private`, `dsn`, `auth` или `uuid` (вместе со всем вложенным поддеревом).
Остальные значения **остаются открытыми** — это сохраняет читаемую структуру, но
требует называть секретные ключи по этим правилам. После шифрования просмотрите
файл: каждое секретное значение должно иметь вид `ENC[AES256_GCM,...]`.

## Ротация получателей

1. Добавьте новый публичный ключ в локальную строку `age: [...]` (или удалите
   выведенный из обращения).
2. Перешифруйте ключ данных для нового набора получателей:
   `sops updatekeys secrets/<имя>.sops.yaml`.
3. При удалении получателя или подозрении на компрометацию дополнительно смените
   ключ данных: `sops rotate -i secrets/<имя>.sops.yaml` (в старых версиях
   `sops -r -i`). Любая копия файла, зашифрованная для скомпрометированного
   ключа, остаётся читаемой, поэтому сами секреты (пароли, токены) тоже нужно
   сменить в соответствующих сервисах.
4. Проверьте `sops -d` новым ключом и уничтожьте старый закрытый ключ.

## Почему зашифрованные файлы здесь не публикуются

План предполагает хранение `secrets/*.sops.yaml` в Git, но действующая политика
публикации (`scripts/check_repository.py`) запрещает каталог `secrets/` в
публичном репозитории, и эта задача её не ослабляет. Даже зашифрованный файл
раскрывает имена ключей, открытые по `encrypted_regex` значения, получателей и
историю изменений, а шифротекст в публичной истории остаётся навсегда: утечка
закрытого ключа в будущем раскроет все прошлые версии. Поэтому файлы
`secrets/*.sops.yaml` остаются локальными, пока владелец явно не изменит
политику отдельным решением.

## Проверка `scripts/check_secrets.py`

Hook `secret-material` выполняется после `repository-policy` в `make check` и в
локальном pre-commit hook. Он читает список `git ls-files -z` (tracked и
staged new файлы), берёт содержимое из индекса Git, а не из рабочего дерева,
не обращается к сети и не вызывает `sops` или `age`. Ошибка выводится как
`правило: 'путь'` без содержимого файла.

| Правило | Условие |
| --- | --- |
| `private-path` | путь запрещён политикой публикации: `secrets/`, другие приватные каталоги, `.env`, ключи, `age-keys.txt`, `*.agekey`; содержимое таких файлов не читается |
| `age-secret-key` | файл содержит маркер закрытого ключа age |
| `private-key-block` | файл содержит заголовок закрытого ключа PEM или OpenSSH |
| `sops-envelope` | `*.sops.yaml`/`*.sops.yml` (кроме самого `.sops.yaml`) без верхнего `sops` с непустым списком `age` (`recipient` вида `age1...` и блок `enc`), `mac` вида `ENC[AES256_GCM,...]` и `lastmodified` |

Игнорирование в `.gitignore` не защищает файл, который уже отслеживается или
добавлен через `git add --force`: такие файлы остаются в индексе, и проверка их
находит. Untracked-файлы не читаются.

Что проверка **не** доказывает:

- что файл расшифровывается, `mac` корректен или получатели принадлежат
  оператору — проверяется только структура;
- что все секретные значения зашифрованы: открытые по `encrypted_regex` значения
  не анализируются;
- отсутствие других секретов: токенов, паролей, API-ключей, закодированных или
  разделённых на части ключей;
- отсутствие секретов в истории Git, в неподготовленных изменениях рабочего
  дерева и в untracked-файлах.

Unit-тесты запускаются отдельно и не входят в `make check`:

```sh
.venv/bin/python -m unittest discover -s scripts/tests --verbose
```

`make check` не заменяет CI job `Secret scan`: он отдельно сканирует доступную
историю Git через gitleaks. Локальные hooks не заменяют серверную защиту ветки.
